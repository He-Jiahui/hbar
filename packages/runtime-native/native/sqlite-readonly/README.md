# Windows readonly SQLite scan extension

This extension supplies a nondefault VFS for fixed-query, short-lived readonly scans. It uses the SQLite engine already loaded by Bun. It does not link another SQLite engine or change the default VFS. Main database reads use an aligned, fixed 64 KiB buffer and `FILE_FLAG_NO_BUFFERING`; the original win32 VFS retains file locks, WAL, shared memory and all other operations. Configured mmap values remain unchanged, while this VFS explicitly declines mapped reads through xFetch.

Each bootstrap owns its VFS name and canonical existing-directory scope. Scopes must resolve to fixed local NTFS volumes. File identity is checked again when opening the separate direct-read handle. SQL-function and open-file references release owner state independently. There are at most 64 owner contexts. One successful initializer retains the extension code until OS process exit; subsequent successful initializers use ordinary connection references. This code lifetime is distinct from owner, registration, handle and buffer cleanup.

`hbar_readonly_scan(path)` visits every original file byte with fixed buffers, rejects short reads and verifies file size and last-write metadata before closing the scan handle. It returns a byte count rather than file contents. The TypeScript adapter exposes only complete pre-read, fixed quick_check, bounded statistics and close operations. It exposes neither the private Database object nor arbitrary SQL. Product business connections retain their original strict parameter binding.

Build with `bun scripts/build-readonly-sqlite-native.ts` from an x64 Visual Studio Developer environment with clang-cl/lld-link. `native:build` includes this step. The generated `../hbar_sqlite_readonly.asset` contains the Windows DLL; the file loader preserves its bytes in an immutable bundle asset. On other platforms the build writes an unused marker and existing SQLite readers remain responsible for scans.

`openReadonlySqliteScan(databasePath, nativeDirectory)` requires a short, absolute physical resource directory owned by the caller's runtime package. Workers in the same package share that directory. The adapter publishes one complete DLL atomically, verifies its SHA against the source, emitted or embedded bytes, and reuses it across scans. It rejects a different existing DLL and never overwrites a loaded module. The native resource remains available through OS process exit; scan owners, VFS registrations, handles and buffers close independently. Resource paths must stay below 248 characters because the observed Bun SQLite extension loader rejects long paths even with a Windows namespace prefix. Runtime package composition remains responsible for choosing and retiring its resource directory.

The adjacent `sqlite3.h` and `sqlite3ext.h` are SQLite 3.53.2 public-domain API headers inherited from the validated prototype. Only trailing whitespace in three sqlite3ext.h comments was removed; API declarations are unchanged. They contain declarations only; SQLite implementation source is not compiled here. The source fixes originate from the independently audited multi-owner prototype, followed by the product scope, complete sequential scan and direct-handle I/O-priority additions.

Primary contracts: [SQLite extensions](https://sqlite.org/loadext.html), [VFS registration](https://sqlite.org/c3ref/vfs_find.html), [SQL function destructors](https://sqlite.org/c3ref/create_function.html), and [Bun file-loader paths](https://bun.com/docs/bundler/loaders).
