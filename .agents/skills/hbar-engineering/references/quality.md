# 类型、检查与逐子功能交付

## 严格 TypeScript 与 lint

- 保持 `strict: true`、`noUncheckedIndexedAccess: true`；严格配置还应启用 `exactOptionalPropertyTypes`、`noImplicitReturns`、`noFallthroughCasesInSwitch`、`noUnusedLocals` 和 `noUnusedParameters`。接入时修复真实问题，不能添加大范围例外或排除业务目录绕过检查。
- 新增业务代码禁止显式和隐式 `any`。未知外部值用 `unknown` 并校验/缩窄；优先泛型、判别联合和从 schema 推导类型。第三方声明内不可控的 `any` 必须在适配边界隔离，不能流入公开接口和业务数据。
- 禁止使用 `as any`、无依据的双重断言、滥用非空断言、`@ts-ignore`、`@ts-nocheck` 或全文件禁用 lint 来让检查通过。确需针对上游类型缺陷使用局部例外时写明原因、范围和可验证依据，不能成为普通实现手段。
- 导出的跨模块函数、服务端口、action、协议及错误类型必须有明确契约；内部实现允许类型推导。Promise 必须被等待或显式处理失败；单独加 `void` 不能替代错误处理。
- 使用支持类型感知的 TypeScript linter，优先 ESLint + typescript-eslint，配合 React Hooks 和依赖边界规则。最低覆盖：显式 any、unsafe assignment/call/member access/return/argument、floating promises、misused promises、穷尽分支、Hooks 规则、循环依赖与非法深层导入。
- lint 覆盖受维护的源码、脚本、测试和配置；生成文件按明确路径排除。警告按失败处理，自动化命令不得用 `|| true`、忽略退出码或 `--no-verify` 掩盖失败。
- 启用 `bun run lint`，统一 `bun run check` 串行执行 lint、typecheck 和基础测试并传播失败退出码；自动化验证复用同一入口。Prettier 只负责格式，不能代替 lint、类型或架构检查。

## 现有工具链的接入

创建本规范时，仓库已有 `typecheck`、`test`、`check`、`build`、`test:e2e`、`bench`、`format:check`，但没有 `lint`，上述额外 TS 选项也未全部启用。开始任务先核对实时配置。

- 若任务只是创建/修改规范，记录差距并校验文档即可；不得顺带升级依赖或宣称严格 lint 已开启。
- 执行代码功能任务时，缺少强制检查属于需要解决的工程前置项。将最小工具链接入及必要修复作为独立、可验证的提交，再交付功能；不能跳过 lint 后宣称功能完全通过规范。
- 如果接入暴露大量跨领域历史问题，应给出具体失败、影响范围与可单独验收的迁移单元，在当前任务可处理的范围内继续推进。需要扩大范围时明确说明尚未完成的门禁，不得悄悄全仓重构，也不得假装检查通过。

## 完成定义与测试

1. 开始功能前确定用户入口、输入、输出、操作对象、状态机及完成条件，确认所属模块与端到端契约。
2. 实现当前功能的完整闭环及适用的失败/恢复路径，保持拆分后的各模块可独立理解和验证。
3. 按风险测试可观察行为，不以只检查函数调用或匹配实现文本的测试充数。业务规则测单元/用例，跨端契约测集成，用户流程测 E2E。
4. 代码提交运行严格 lint、typecheck 和基础测试；Web 改动执行 build，交互改动执行相关 E2E 与截图检查，协议/并发改动增加相应集成与基准。桌面改动按 `docs/testing.md` 验证构建和 smoke test。
5. 检查改动文件格式与 `git diff --check`。避免为通过全仓格式检查而夹带无关格式化；历史失败与本次失败分别记录，未通过的门禁不可标记完成。
6. 文档技能修改运行技能 validator、变更文档格式检查与相对链接检查。无需为纯文档改动声称执行了业务回归。

测试用临时数据、fixture 和仓库既有机制；不得依赖真实付费模型或污染用户数据。报告实际运行的命令、结果、跳过项目及原因。失败后修复并重跑相关检查；检查通过后不无意义重复全套测试。

## Git 与目录纪律

- 开工先检查 `git status --short` 和已有 diff，识别用户改动、已暂存内容及当前分支。将大功能拆成可独立验证的子功能，每个子功能完成并测试通过后立即进行本地 commit，再进入下一个子功能；不得等整个大功能结束或积攒多个已完成子功能后集中提交。提交粒度以完整、可验证的行为为准，不按文件数机械拆分。
- 目录按既有 workspace 和功能归属组织；禁止随意创建根目录临时文件、`final2`、重复实现、废弃组件、备份副本和用途不明的公共目录。移动文件同步修复导入、公开入口及文档链接。
- 测试截图、报告、构建产物和本地运行数据放进已有忽略目录，如 `artifacts/`、`test-results/`、`playwright-report/`、`.dev/`，不暂存秘密、凭据或这些产物。
- 暂存时显式指定本功能路径或使用可核对的局部补丁，避免无差别 `git add .` / `git add -A`。提交前查看 `git diff --cached`、`git diff --cached --check` 和 `git status --short`。
- 若用户已有暂存或同文件混合改动，先检查内容并采用隔离本次改动的提交方式；不得夹带、还原、清理或自动 stash 用户改动。不能可靠隔离时如实说明未能提交的原因。
- 提交标题说明目的，沿用仓库风格，如 `feat(web): ...`、`fix(host): ...`、`chore(quality): ...`、`docs: ...`。提交正文记录关键行为变化、实际验证命令及结果；修复还需记录症状、已证实原因和相关提交 ID，未确认的原因明确标为假设。每个提交应可独立检查，不提交已知失败的半成品来满足“立即”。
- 提交后核对 commit 内容和 `git status --short`，确保本次子功能无未提交或遗漏的文件。任务开始时工作区干净且没有其他任务改动时，提交后也必须干净；用户及其他任务的既有改动保留并区分，不得通过夹带提交、删除、还原或自动 stash 制造“干净”。
- 本规范要求本地 commit，不自动授权 push、发布、合并或改写历史。不得擅自 amend 已有提交或 force push。

## 问题优先查证 Git 历史

1. 记录症状、复现步骤、预期与实际结果、运行环境和当前 `HEAD`；先查看 `git status --short`、`git diff` 与 `git diff --cached`，区分已提交代码和本地改动。
2. 在推测原因或修改代码前，优先查看相关路径的 `git log --oneline -- <path>` 和候选提交的 `git show <commit> -- <path>`，核对近期变更目的与验证记录；不只看提交标题就认定原因。
3. 根据线索使用 `git log -S '<symbol>' -- <path>`、`git log -G '<pattern>' -- <path>`、`git blame -L <start>,<end> -- <path>` 或已知正常版本与异常版本之间的 `git diff` 缩小范围。blame 指向的最后修改者/提交只是线索，不是故障因果证据。
4. 用可重复测试或最小复现验证候选差异。必要时在独立 worktree 中对比历史版本或执行有界 `git bisect`，不在含用户或其他任务未提交改动的工作区切换历史版本、reset 或清理文件。
5. 记录正常/异常版本、已证实的引入提交（若能确认）、根因、最小修复和回归测试。历史证据不足时明确说明，并继续检查日志、配置、依赖和运行时数据，不能强行归因于最近一次提交。
6. 修复验证通过后立即独立提交，将关联提交 ID、复现条件和回归验证写入提交正文，形成可追溯记录。详细测试输出可留在既有忽略目录，关键结论必须随提交保留，不能只存在临时文件或对话中。

交付回复简洁说明完成的行为、关键文件、验证结果、commit ID 和实际遗留问题。子功能未完成、门禁失败或提交失败时明确说明，不用完成措辞掩盖缺口。
