# 输入缓存修复验收记录

日期：2026-10-16。环境：Windows x64，Bun 1.4.0，hbar 真实 Kernel / PiDriver，`https://api.niumacode.cc/v1/responses`，`gpt-6.1-sol`，XHigh，流式。所有真实请求均使用隔离工作区、临时数据库及内存凭据；没有改写用户历史。失败样本全部保留，没有自动重试补成绩。

## 门禁与方法

每会话最多 12 次请求：冷启动一次，11 次连续工具调用形成后续请求。每次工具返回不同的源码片段（2,400 字符），每轮更新 Host 状态。总体按 `ΣcacheRead / Σinput` 计算，包含冷启动；总体必须 >90%，最近连续 10 次各 ≥95%。脚本进一步要求全部 11 次非冷启动请求各 ≥95%，并验证步骤、样本、Run 状态及实际 XHigh 配置。

这衡量受控调用链的实际服务响应，不能代表任意新会话、模型切换、压缩或长时间间隔的保证。自然业务请求仍以工作台中的真实指标为准。

## 已证实的客户端原因

1. `d5e47a1` 引入的工作流动态工具压缩会改变工具 manifest 和首条 developer 消息。修复在 Run 内固定 schema、说明与顺序，权限和 scope 仍在执行时校验。
2. `b7aff23b` 已把动态 Host 事实移至历史末尾，但下一轮会替换原后缀。历史增长时，已发送的完整输入不再是精确前缀。修复以会话、协议及版本限定的 assistant 元数据保留快照，并在原位置恢复；快照参与容量估算及压缩，子会话 seed 和摘要不继承旧快照的指令权威。
3. 当前牛马 Responses 确实返回 `x-codex-turn-state`，但 pi-ai 1.1.0 没有保存和回带该字段。PiDriver 已补齐首次状态在同一 Run 中的回传，并在路由或凭据改变时退役；没有持久化或记录不透明原值。此处证实的是协议遗漏，尚不能认定它解释了全部低命中。

## 兼容性与交付边界

牛马当前模型明确拒绝 `prompt_cache_breakpoint`（HTTP 400，not supported on this model），因此没有启用该参数或在失败后自动补发付费请求。OpenAI 原生能力以[官方缓存指南](https://developers.openai.com/api/docs/guides/prompt-caching)及[诊断说明](https://developers.openai.com/api/docs/guides/prompt-caching/diagnostics)为准，不能据此推断第三方兼容实现支持全部字段。

另做不包含显式断点的独立诊断探测：两次请求输入逐字相同，第二次仅增加 `prompt_cache_options.comparison_response_id` 指向第一次实际完成的 response ID，并回带首次路由状态。两次均 HTTP 200、输入 9,211、缓存读取 4,096，但最终事件均未提供 `prompt_cache_diagnostics`。因此已证实参数没有导致本次 HTTP 失败，尚未证实网关转发或实现了该诊断能力；不能把缺少诊断视为命中，也不能将其误记为被明确拒绝。两次请求的结果保留在 `artifacts/input-cache-verification/diagnostics-capability.json`，没有追加重试。

指标、界面和严格失败门禁已实现。串行受控调用链已实测达标；**并发稳定 ≥95% 尚未通过，不能宣称整体目标完成**。前端会如实显示这些失败，后续需结合网关服务端证据处理剩余异常。

将最终串行及第二轮并发失败会话的真实用量送入同一生产前端组件，宽屏和 320px 深色窄屏均正确显示对应门禁。串行显示总体 91.32%；并发失败显示总体 83.09%、近期最低 0%，没有把异常平均隐藏。结果与上表记录一致。这是从已保存的真实用量进行的组件回放，未向运行中的用户会话注入数据。
