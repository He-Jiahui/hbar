# Shared branch launch

This change delivers the Host and Runtime preparation capability. The Location picker integration and its visual/real-Host checks land separately; this document does not claim that UI has been delivered by this commit.

An existing local branch selection is a launch choice, not an immediate checkout. The selection contract captures the branch page's local ref and tip OID in the draft; setting that choice does not switch the repository. First Send transfers that captured choice to the existing session launch-target preparation operation.

The selection is represented as `{ mode: 'shared-branch', branch: { ref, tipOid } }`. The Host resolves the registered workspace, verifies that the ref still points to the captured tip and is not checked out in another worktree, persists the existing revision-scoped preparation intent, then performs a non-forced local `git switch`. As with Host-managed worktree preparation, the switch supplies a Host-owned, prechecked nonexistent `core.hooksPath` so repository post-checkout hooks do not execute implicitly during first-send setup. Readiness is reported only after the shared checkout's symbolic HEAD, commit OID, and selected ref all match the captured branch. No new worktree or branch is created. The session target and Run cwd remain the registered workspace path, so Files and Git stay associated with the original project.

`shared-current` remains a separate choice: it uses the current checkout without a branch mutation and continues to have null branch/head binding fields. `isolated-worktree` remains unchanged: its selected branch is a base and the Host prepares a managed worktree. A shared-branch binding stores the initial selected branch and confirmed HEAD for atomic first-Run admission. After acceptance, shared sessions follow the checkout's current branch and HEAD; subsequent verification still requires the same workspace path. The original selection stays as launch history, not a promise that the shared branch remains pinned.

The Kernel coordinates shared-branch mutation and Run admission with a short lock keyed by canonical checkout root. It checks Storage's bounded active shared-checkout paths (queued, running, or awaiting approval) before a switch, including sibling sessions that use the same checkout. This is a single-Host coordination boundary: it does not lock external Git processes, another Host using the same repository, or filesystem changes made outside hbar.

If the captured ref moved before checkout, preparation fails without switching. Git's ordinary switch behavior is used: there is no force or discard flag, so conflicting local edits are not overwritten. If a switch may have started but the Host cannot prove the captured target on read-back, the target remains reconciling. Cancellation/restart reconciliation never switches back automatically and never claims cancellation merely because the target branch is not currently visible. The user must inspect or explicitly reselect before a new attempt.

The first accepted Run still freezes this session's launch record. If another session or external Git later changes the shared checkout to a different branch, returning to the earlier session continues at the shared path without silently switching it back. This matches CC's shared A-to-B-to-A continuation. Use an isolated worktree when an independent execution branch is needed. The initial implementation in `8bad4c80` checked the saved shared branch after acceptance; reference review showed that this over-pinned a launch-only choice, so the follow-up removes that post-acceptance check while preserving exact branch/tip verification before first admission. Post-switch uncertainty can still require manual inspection because the existing preparation journal does not store the original checkout ref/HEAD; the UI must not promise that Cancel rolls back or immediately unlocks every uncertain operation.

Reference evidence at CC `e28d0a653`: `desktop/src/components/chat/ChatInput.tsx:268,793-823` gates the launch choice on an empty session; `src/server/services/conversationService.ts:346-393` reuses running sessions and only prepares the selected branch when not resuming; `src/server/services/repositoryLaunchService.ts:723-772` implements the initial shared checkout. These are source-level semantics, not new native screenshots or concurrency guarantees for CC.

Relevant implementation boundaries:

- `SessionLaunchTargetService.checkoutRootForWorkspace` supplies the checkout lock key; for non-Git workspaces and non-cancellation Git inspection failures it falls back to the canonical workspace path so legacy shared-current sends remain available.
- `SharedBranchCheckoutGuard` runs only immediately before a required checkout. It receives the session, canonical Git checkout root, and the preparation signal.
- `verifyPreparedSharedBranch` checks the captured tip before first Run admission. `verifyBoundTarget` checks the shared path after admission without pinning a shared branch forever.

The focused temporary-Git suite is `tests/session-launch-shared-branch.test.ts`. It covers delayed checkout, a moved ref, dirty checkout conflict, prepared-state mismatch without rollback, and a later HEAD advance after Run binding. Tests use only temporary repositories and Host data directories.
