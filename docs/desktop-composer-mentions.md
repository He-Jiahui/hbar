## hbar behavior and capability boundary

The CodeMirror editor stores display text plus up to 40 validated non-overlapping `{start,end,label,path,workspaceId,directory}` spans in the session's existing draft state. The local `draft.setContent` command updates both under one expected revision. A Host `file.find` result supplies bounded workspace-relative **files**; `file.list` supplies folders and paged entries. Candidate selection must still match the currently visible search result, session, workspace, trigger text and revision. Path validation rejects absolute/drive paths, traversal, empty segments, backslashes and control characters. Typing the same visible token manually never creates a span. On `composerIntent.submit`, only valid spans from the captured draft revision are serialized as `@"relative/path"`; the original display text remains for failed/unknown submissions and is cleared only by the existing confirmed receipt logic. It does not upload or automatically read a file.

The popup supports mouse selection, folder navigation, Arrow Up/Down, Enter/Tab selection, Arrow Right folder navigation, Escape, Shift+Enter newline and IME composition confirmation without sending. Query requests debounce for 120 ms; identity/revision checks discard late results because the browser command transport does not offer end-to-end cancellation. A disconnected menu reports the loss of search capability while retaining the draft. `file.find` explicitly reports truncation; directory paging is bounded to 200 visible candidates and reports that cap. The underlying `file.list` provider currently returns at most 1,000 directory entries without a separate truncation flag, so the UI does not claim exhaustive discovery at that limit. The Host's existing hidden-entry policy remains unchanged (it may expose `.git`); the composer does not silently invent a different filter.
