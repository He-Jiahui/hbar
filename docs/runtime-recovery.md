# 运行单元恢复与热重载

此架构首次安装需要停止旧 Host 并启动受管入口，完成前向数据库迁移 25。迁移同时补齐版本 24 两种历史布局中的恢复记录与 Run 文件变更表。后续兼容业务更新可局部应用；稳定底座、原生二进制或不兼容存储迁移仍明确要求重启。源码开发、CLI 自动启动、桌面开发与打包入口均使用同一受管组合。

## 所有者与路由

标准组合有 14 个业务单元：Controller、Kernel、Pi、Storage、Maintenance，以及 Local、Plan、Budget、Goal、Git、Agent、Workflow、Browser、Computer 9 个插件。Storage 和 Maintenance 各自持有所属 Worker。加上稳定 Host 和 Supervisor，正式入口常驻 16 个 Bun 进程；候选与排空旧代会暂时增加进程。自定义 profile 通过受管 Kernel 保持兼容，其无法隔离的模块更新返回需要重启。

稳定 Host 持有 HTTP/WS 监听、身份和鉴权、连接原生句柄、系统终端、状态订阅和协调端口。Controller 持有请求/命令适配；Kernel 持有用例与调度。业务单元替换不轮换 Host 身份或设备凭据，系统终端属于稳定入口，已有浏览器上下文通过显式资源租约保留原版本。

每个 Run 绑定 Kernel、Pi 或 legacy driver、插件和 Hook 版本集合。同一 Session 只允许一个执行者；旧 Run 的取消、审批、进度和提交仍归其所有者，完成后交接，新排队输入再使用当前版本。执行权撤销后，旧进程的迟到提交被拒绝。checkout 锁、物理工具容量、资源所有权和维护门禁跨代共享。

## 准备、切换与排空

更新顺序为变更归属、构建候选、兼容和就绪检查、切换默认路由、旧代排空、资源释放。Bun metafile 的真实输出贡献、存活 re-export 绑定、公开契约指纹、插件依赖和声明资源共同确定归属。新增、删除与重命名继续使用 400 ms 防抖；共享代码更新实际依赖单元，被消除的无用实现不会扩大重载。

产物按内容哈希登记，准备和每次故障恢复前再次验证不可变字节。候选在只读端口构造真实 Kernel/插件/Worker，检查数据库 schema 与完整性，不能取得生产写入权、启动调度、恢复旧任务或执行外部副作用。准备失败保留当前服务版本。激活确认之后先取得新实例的描述与投影，再开放服务；激活等待期间仍由可服务的旧实例承接已有兼容请求。

每个单元最多两代服务版本，另允许一个候选；准备并发为 2。容量不足时保留最新候选，后续修改合并。取消只撤销尚未切换的候选。切换授权后失败，新版本仍是恢复目标，持续退避重建，不自动回退。开发监听在每次构建前清理无引用的登记元数据，保留活动/恢复代、排队候选、未结束操作及最近 128 个产物集合；过期集合返回 `RUNTIME_ARTIFACT_UNREGISTERED`。磁盘不可变产物不在在线运行时自动删除。

## 请求、连接与进程恢复

请求校验、业务错误和响应序列化失败结束所属请求；单客户端发送、订阅者、队列/定时器和资源回调错误各自隔离并记录诊断。连接发送失败不会中断其他连接的广播。SDK 首次连接失败继续退避重连；只有显式断开或鉴权撤销停止重连。事件从连续已应用游标恢复，回放窗口过期时受控补取快照。

未捕获异常、未处理 rejection、异常退出或心跳失联使所属单元退出服务并重建。心跳 2 秒、连续 3 次失联，启动期限 120 秒，每个单元关闭/释放期限 5 秒；故障先撤销逻辑执行权，无法确认物理退出时保留执行容量、资源与写入门禁，不开启另一个写入者。恢复延迟先 250 ms、1 秒、4 秒，再每 30 秒低频尝试并加入抖动，连续健康 60 秒重置快速计数。主动关闭停止恢复，不会把已关闭的服务重新拉起。

`/livez` 独立于业务单元，稳定监听存活时返回成功。`/healthz` 和运行时快照反映必要单元与写入/执行门禁就绪情况。故障期间可查询状态；受影响命令返回明确的恢复代码，无关功能继续服务。Windows 原生 Job 实测覆盖所属子孙进程退出和 Root 退出后的清理；Unix 进程组实现已提供，但本次 Windows 验收没有执行 Linux/macOS 原生验证，不宣称覆盖主动脱离进程组的原生程序。

## 安全续跑与结果对账

故障恢复只处理原所有者的 Session/Run，候选不调用全局恢复或 Goal 启动恢复。先撤销执行权并确认物理执行退出，随后核对规范日志、工具意图与回执。原 Run 保留真实 interrupted 终态；符合续跑条件时，以持久恢复标识创建新 Run，记录 predecessor/root/chain 关系。重复故障通知和丢失的恢复提交确认通过同一标识对账，不能生成多个恢复轮次。

已提交用户消息、上下文、已结算工具结果及 checkout 绑定复用，未执行队列保留身份。副作用已发生但结果未确认时保持 `EFFECT_UNKNOWN`，未决审批保持 `APPROVAL_PENDING`；即使有驱动完成回执，也不能绕过未知副作用。`run.driverCompleted` 已提交且没有未决操作时只收敛终态，不再次请求模型或重复结果；原 Run 仍保持中断，后续 Run 记录完成。

继续执行重新检查取消、归档、权限/沙箱、模式、模型、预算和 Goal 状态，不扩大授权；用户排队输入优先于自动续跑。每条恢复链最多两次自动续跑，之后保留人工继续状态。`run.retry` 在原链中持久记录人工继续回执，去重并保留已经消耗的自动次数；整个链最多 32 个续跑轮次。未知副作用、审批、暂停或其他原控制仍不能由人工重试绕过。CLI 等待器与 Web 运行投影跟随恢复链，观察后续 Run 的真实终态。

## 唯一存储写入者与维护

所有代通过稳定 StoragePort 访问数据库。候选先只读检查实际 Worker；切换停止向旧写入者接纳新调用，排空事务并确认旧 Worker、所属进程和 OS lease 实际退出，再开启新写入者。等待队列、字节与期限都有界。已派发调用失去确认时不会自动重放；纯读取故障允许校验后恢复，结果不明写入保持不可写状态，且在验证前不会启动另一个写入者。

Maintenance 独立管理作业和回执，已有作业保留原代，新作业使用当前代。数据库维护门禁全局共享；先暂停普通写入并排空所属 Worker，完成实际退出后进行维护，结果对账与完整性确认后恢复 Storage。VACUUM 超时或丢失确认通过验证 Worker 核对，不能重做未知写入；完整性不明则继续保留门禁。

## 查询和应用已登记版本

通过现有 command catalog 调用以下接口；不能传任意模块路径或远程代码。源码开发使用 `HBAR_RUNTIME_WATCH=1` 自动构建并应用。正式源码部署可使用 `HBAR_RUNTIME_WATCH=prepare`：监听只构建、登记并报告 `prepared` 集合，不切换任何运行单元；操作方再通过已登记的 `artifactSetId` 显式应用。构建打包器和本地嵌入 API 也可登记产物集合，运行时快照列出可用 ID。无源码的打包入口使用 build-pinned 产物；此监听不能成为加载任意新代码的网络接口。

| 命令 | 输入 | 结果 |
| --- | --- | --- |
| `system.runtime.get` | `{}` | 单元、代际、恢复原因/下次尝试、就绪与门禁、已登记集合 |
| `system.runtime.reload` | `{ artifactSetId, unitIds }` | 尽早返回 `{ operationId }` |
| `system.runtime.reload.get` | `{ operationId }` | 准备、等待容量、切换、排空或失败状态 |
| `system.runtime.reload.cancel` | `{ operationId }` | 仅撤销尚未切换部分，返回操作快照 |

例如 `hbar exec system.runtime.get --input-json '{}'`；应用版本时使用 `--input-json` 传上述对象，再查询返回的操作 ID。状态按需订阅，保留 64 个增量窗口，每批最多 32 个单元、16 个操作。Web 的现有连接状态和诊断入口展示准备、排空、恢复、失败与需要重启，使用宿主提供的中英文类型化文案和原有 Lumen 工作台。

IPC 默认每方向 32 个在途、128 个排队，两方向合计每单元最多 64 个物理调用、256 个排队调用，保留控制调用容量。消息最多 32 MiB，使用有界分块和最多 64 MiB 缓冲；大型数据不直接传递原生句柄。全 Host 物理工具执行上限为 64，超时但尚未真实退出的执行继续占容量。

## 实测与验收

验收命令、日志和最终结果见[验证说明](testing.md#运行单元恢复与热重载验收)。`bun scripts/measure-runtime.ts` 在独立本地数据目录运行 8 个 Session、16 个 mock Run、8 个并行查询；只使用本地 mock 模型，并将驱动完成延迟 10 秒以保留旧代。它检查旧/新 Run 分别绑定 Kernel 1/2、13 个无关单元 PID 不变、全部 Run 完成和 WebSocket 保持，并保存 `artifacts/runtime-measurement/result.json`。

2026-10-11 Windows / Bun 1.4.0 测量：基线 128 次查询 p95 **39.27 ms**、max **43.76 ms**；Kernel 重载期间 512 次查询 p95 **204.05 ms**、max **435.24 ms**。单元物理调用采样峰值 **25**，IPC 与 Storage 等待队列采样峰值 **0**，单元合并缓冲采样峰值 **1,481,026 bytes**。这是该 workload 的采样结果，不能代替容量饱和测试或承诺更大负载下的延迟。

该本地测量直接启动稳定 Host，不包含 Supervisor，常驻 **15**、候选峰值 **16** 个 Bun 进程。所属进程 Windows `WorkingSet64` 总和峰值 **3,836,735,488 bytes（约 3.57 GiB）**，共享页可能重复计入；没有把它当作私有内存或全系统 RSS。测量与其他验收共用机器，未设性能通过阈值。正式受管入口额外包含一个 Supervisor，其实际拓扑由 standalone CLI 和原生桌面 smoke 验证。
