# Device appearance draft and recovery

The published cc-haha General settings image (`D:/Git/cc-haha/docs/images/app/zh-CN/settings-general.webp`) shows a follow-system switch, directly visible theme choices and language choices. Its `desktop/src/pages/settings/GeneralSettings.tsx` calls theme/locale setters on selection. Hbar presently supports System/Light/Dark and the browser's startup locale; this change does not claim cc-haha's six palettes, five language choices, or immediate persistence.

Hbar Appearance remains an explicit device-local Save/Restore defaults form. Its draft belongs to one connected runtime and survives switching settings categories, returning to the original session, and reopening settings. Discard changes only that draft. A new Host runtime/window gets its own editor; neither navigation nor its draft writes Host session settings. The live preview reads the draft, while the workbench theme and size read confirmed device preferences.

Appearance writes use the existing serialized `preferences.set`/`preferences.unset` revision CAS. A multi-field Save/Reset can commit an earlier field before a later field fails. On a conflict or ambiguous write, the editor keeps the original draft and prevents further writes. **Check saved values** re-reads the device preference envelope behind pending writes; it never replays a write. If the current saved values already match the requested result, the editor confirms it. Otherwise it presents the current saved appearance, reports how many draft changes currently match, and requires an explicit choice: keep the original draft against the newly confirmed revision and press Save again, or discard the draft in favor of the confirmed values. A partial Reset has distinct copy: keeping the old draft does not continue resetting; accepting the current values permits a new, explicit Restore defaults.

If restoring the preference envelope fails, `preferences.set` and `preferences.unset` reject before writing, the form disables Save/Reset/Discard and offers a read-only retry. The last bootstrap theme may still render the UI, but it is not described as a confirmed persisted preference. A command returning `persisted:false` is reported as effective for this run only, not saved across restart. This is a local-client preference workflow, not a new Host RPC or a transaction spanning four keys.

Verification: `tests/appearance-editor.test.tsx` covers independent runtimes, conflict after a first committed key, plain post-write unknown result, partial Reset, restore failure and volatile success. `tests/client-persistence-runtime.test.ts` checks the write guard and read-only recovery from invalid saved data. Real temporary Host pairing in `e2e/appearance-draft-recovery.spec.ts` checks both locales, 1440/320 widths, draft through categories/Back, confirmed Save, partial write and user-directed reconciliation, and read-failure recovery. Screenshots in ignored `artifacts/reference-ux-v2/appearance-draft-{locale}-1440.png` show the unsaved draft; `appearance-partial-{locale}-320.png` shows the checked partial result. The reference screenshot is published visual evidence; these hbar screenshots are test captures from a temporary Host.

At 320px the settings pane itself scrolls. `appearance-recovery-actions-{locale}-320.png` captures its recovery controls after scrolling into view; the first narrow screenshot crops those controls because they are below the initial viewport, not because they are unreachable. The light-theme preview's muted text has weak contrast when the surrounding app is dark in these captures. That is a separate visual-token correction, not a change to this draft/recovery unit.
