# GitHub Flow

hbar 使用轻量的 GitHub Flow：`master` 始终代表可集成的主线；每项改变在短生命周期分支和 Pull Request 中讨论、验证并合并。发布分支、长期集成功能分支和在 PR 之外累积大量不相关改动都不是默认流程。

## 日常流程

1. 从最新 `master` 创建一个单一目的分支，例如 `feat/session-export`、`fix/pairing-timeout` 或 `docs/wiki-onboarding`。自动化代理创建的分支可使用 `codex/<topic>` 前缀。
2. 以完整可验证的子功能为粒度提交。不要夹带无关格式化、生成物、密钥或其他人的未提交改动。
3. 按改动范围运行检查；基础门禁是 `bun run check`、`bun run build`，文档还要运行 `bun run check:docs`。
4. 尽早打开 Draft PR，说明影响面和尚未完成的验证；准备合并时再标记为 ready for review。
5. 由作者和审阅者共同核对行为、测试证据、失败/恢复路径及回滚方式。CI 绿灯不替代审阅，审阅也不替代可重复的检查。
6. 通过审阅和受保护分支要求后合并到 `master`，删除已合并的短生命周期分支。是否使用 squash merge 由仓库设置决定；无论采用何种合并方式，都要保留清楚、可追溯的提交意图。

## PR 应说明什么

每个 PR 至少包含：

- 变更内容与影响范围；
- 已运行命令及实际结果；
- 对 UI、协议、存储、插件或安全边界的兼容性/迁移说明；
- 尚未覆盖的风险、已知限制与安全回滚方式。

生产行为变化应有同领域测试。涉及跨端、流式、并发、取消、重连、恢复或权限时，不要只验证函数被调用；应验证用户能观察到的最终状态和失败路径。

## 建议的仓库设置

工作流文件可以提供检查，但不能自行开启 GitHub 的分支保护。管理员应在仓库 Settings 中为 `master` 配置至少以下规则：

- 要求 PR 才能合并；
- 要求至少一位批准审阅者；
- 要求当前分支已更新到合并基线；
- 将 CI 的 `verify` 状态设为 required，禁止绕过失败检查；
- 限制 force push 与直接删除受保护分支。

这些是仓库设置，不会由代码提交自动修改。启用原生 GitHub Wiki 后，也应设置仅由受信任的 `master` 推送发布 Wiki，避免 PR 代码接触发布凭据。

## Wiki 发布约定

`docs/wiki/` 是 GitHub Wiki 页面唯一规范源。不要只在 GitHub Wiki 网页编辑：否则下一次发布会覆盖未回写到主仓库的内容。更新页面时同时检查 `Home.md`、`_Sidebar.md`、相对链接和发布工作流；发布配置会使用只在受信任主线可用的 token，不在 Pull Request 中暴露任何密钥。
