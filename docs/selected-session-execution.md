# Selected Session execution summary

The read-only `session.execution.get({sessionId, workspaceId})` command returns the exact captured target, the existing directory activity revision and `SessionActivityExecution`. It does not depend on sidebar pagination or expose prompts, messages, titles, Agent-private history or Goal mutations.

Storage validates the Session/Workspace pair and reads its revision and activity in one Worker transaction. The aggregate follows the existing public sidebar policy from `4fa9293d` and `7582dd70`: own nonterminal Runs plus immediate non-fork child Runs, including archived or hidden children because hiding is not cancellation. Forks are independent; grandchildren do not recursively keep the parent active. The exact query filters the Run aggregate to that target rather than paging all Sessions. Cancel-requested and approval states keep their existing precedence. This is Session activity, not proof of Goal completion or exclusive Goal ownership.

The contract rejects contradictory idle/count/queued summaries. The Client's read-only adapter and Runtime Directory query facade both route the command with typed schema validation; the facade checks the returned Session/Workspace pair and does not merge another Session record or keep a second execution cache. The public command category is `session.execution` and the scope remains Workspace-bound. Existing directory discovery contracts are unchanged.

Root independently verified 12 storage/service/real-adapter tests / 110 assertions, strict affected-graph TypeScript, zero-warning ESLint, formatting and staged diff. Tests cover own/child/mixed activity, cancellation and idle, hidden/archived child retention, fork/grandchild exclusion, missing/mismatched target, no prompt leakage, and actual temporary Host/Client adapter routing. The agent's broader typecheck encountered existing preview/shared-UI errors; it is not counted as passing. Its catalog check also found the old workspace-session expected list omits already-existing sidebar commands; the new query's separate category does not expand that mismatch. There is no new native build, provider execution, schema migration, installation or push. No throughput claim is made from these functional tests.
